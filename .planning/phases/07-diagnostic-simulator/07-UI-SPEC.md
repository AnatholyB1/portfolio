# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled CSS design system (no component library), same sitewide system Phase 1-4 shipped and Phase 6 extended |
| Preset | not applicable |
| Component library | none (no Radix, no shadcn, no headless-UI in `package.json`) |
| Icon library | none as the primary convention (text glyphs `✓`/`→`/`←` and inline SVG) — `lucide-react` (already installed, `src/lib/serviceIcons.ts` registry pattern) is available as an *optional* accent on answer-option buttons or result-screen service cards, per `07-RESEARCH.md`'s Standard Stack, but is not required |
| Font | Space Grotesk (`--font-display`, headings/display) · Manrope (`--font-body`, body copy) · JetBrains Mono (`--font-mono`, labels/meta/numerics) — all loaded via `next/font/google` in root `layout.tsx`, exposed as CSS vars in `globals.css` |

**Why "none" and not a shadcn gate prompt:** `components.json` is absent, and this is not an open decision for this phase either — Phase 6's UI-SPEC already settled it for the entire v1.1 milestone (Phase 1-4 shipped a complete bespoke CSS design system; introducing shadcn/Radix for a wizard's form controls would contradict the zero-dependency convention `07-RESEARCH.md`'s own "Don't Hand-Roll"/Anti-Patterns sections confirm holds for this phase too — no new form/wizard/charting library, hand-rolled `useState` + native inputs + inline SVG). Re-running the shadcn gate would relitigate a settled architectural decision. Registry safety gate: not applicable.

## Spacing Scale

Declared values (must be multiples of 4) — identical scale to Phase 6, reused verbatim:

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| xs | 4px | Icon-to-text gaps (`✓`/`→` glyphs next to labels, checkbox-to-label gap) |
| sm | 8px | Answer-option internal padding (vertical), form-field label-to-input gap, RGPD checkbox-to-text gap |
| md | 16px | Gap between stacked answer-option buttons, gap between form fields, gap between gauge and score caption |
| lg | 32px | Gap between wizard nav row and the question/card above it; gap between pillar-intro paragraphs and the wizard's first question |
| xl | 48px | Section gap between pillar intro and wizard; section gap between wizard and FAQ block |
| 2xl | 64px | Gap before the FAQ block's own heading; gap around the result screen's CTA block |

Exceptions:
- **44px minimum touch target** for every answer-option button, the Suivant/Précédent nav buttons, and the checkbox hit area — accessibility floor for tap targets on question/contact screens, overriding the visual padding above when the two conflict on small screens.
- **Progress bar height (4px)** and **gauge SVG diameter (200px, 14px stroke)** are component dimensions, not spacing tokens — declared in Component & Layout Patterns below, not part of the spacing scale.

## Typography

Reuses the existing 3-font system and Phase 6's exact size/weight values — no new sizes invented. Exactly 4 declared sizes, per Dimension 4's cap.

| Role | Size | Weight | Line Height | Font |
|------|------|--------|-------------|------|
| Display (pillar H1; result-screen headline) | `clamp(40px, 6vw, 72px)` (reuse `.sec-title` scale) | 500 | 0.95 | `--font-display` |
| Heading (per-question prompt text, treated as an H2-equivalent per screen; FAQ `<summary>` questions; pillar intro H2 subsections; recommended-service card names) | 32px | 500 | 1.15 (question prompts, section H2s) · 1.25 (FAQ summary / service card names) | `--font-display` |
| Body (answer-option labels, form field labels/inputs, RGPD consent text, pillar-intro/FAQ paragraphs, gauge score number's supporting copy) | 16px | 400 | 1.5 (paragraphs, consent text) · 1.3 (answer-option button labels — short phrases) | `--font-body` |
| Label / meta (progress-bar sr-only "Question X sur Y" text, gauge caption e.g. "Score d'opportunité", step/section mono tags) | 11px | 500, uppercase, letter-spacing 0.15–0.18em | 1.2 | `--font-mono` |

**Weights (exactly 2):** 400 (regular — all body/paragraph/option-label/form-input copy) and 500 (medium — all headings, display, CTA button labels, the animated gauge score number). 700 remains the existing, narrowly-scoped nav-brand/wordmark exception — do not use it anywhere in this phase.

Italic accent (`.it` / `<em className="it">`) — reuse for the pillar H1's benefit clause if the pattern applies (e.g. "Diagnostic gratuit · *sans engagement*"), consistent with Phase 6.

## Color

Reuses the existing shipped palette from `globals.css` — no new colors introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg` `#0A0B0C` | Page background across the pillar intro, all wizard steps (questions, contact-capture, result), and the FAQ block |
| Secondary (30%) | `--bg-2` `#111213` | Question card surface, answer-option buttons in idle/unselected state, contact-capture form card, FAQ `<details>` items, recommended-service cards on the result screen |
| Accent (10%) | `--acid` `#C4F542` | Reserved for: progress-bar fill, radial gauge fill arc + animated score number, selected/active answer-option border + tint (`--acid-soft` background), RGPD checkbox checked state, primary CTA buttons ("Commencer mon diagnostic", "Suivant", "Obtenir mon diagnostic", "Appeler"/"Écrire" on the result screen), focus ring on form inputs |
| Destructive | not applicable | No destructive/irreversible action exists in this phase's UI — no delete, no reset-with-confirmation. In-wizard "Précédent" is a plain non-destructive step decrement (D-15); the browser Back button leaving the page and discarding progress is an accepted, undocumented gap (RESEARCH.md Pitfall 5), not a UI-level action this contract needs to gate with a destructive-confirmation pattern |
| Secondary semantic — "problem/error" | `--warm` `#E07856` | Reserved for: the submission-error state only (icon/border/heading accent on the "Une erreur est survenue" message in the contact-capture step) — consistent with the sitewide "tension" meaning already established for `--warm` in Phase 6's problem sections. **Do not** use `--warm` anywhere on the gauge itself — D-10 locks the gauge to a single acid-green accent regardless of score value, so a low/urgent score is communicated via copy framing (D-11), not via a color change on the gauge |

Accent reserved for (explicit, no other elements): progress-bar fill, gauge fill arc + score number, selected-answer-option styling, RGPD checkbox checked state, primary CTA buttons, input focus rings. Never use `--acid` as a large background fill, for body text color, or on the gauge's *track* circle (track stays `--line`).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA — pillar intro → wizard start | **"Commencer mon diagnostic →"** |
| Primary CTA — advance a question | **"Suivant →"** (disabled/dimmed until the current question has a selected value) |
| Primary CTA — last question → contact step | **"Voir ma recommandation →"** (distinct label from "Suivant" on the final question, signals the transition into the contact-capture gate per SIMU-04) |
| Back navigation | **"← Précédent"** (plain `useState` step decrement per D-15; hidden on the first question; does not clear the previously stored answer) |
| Primary CTA — contact-capture submit | **"Obtenir mon diagnostic →"** (disabled until `consentementRgpd` is `true` and nom/email/téléphone are filled; assembles the payload, POSTs to `/api/simulateur`, advances to the result step on `{ok:true}`) |
| Result screen CTA (SIMU-07 — one action, two channels, never two competing objectives) | Single heading, e.g. **"Parlons de votre diagnostic"**, with two equal-weight buttons beneath it: **"Appeler"** (`tel:` link) and **"Écrire"** (`mailto:` or `/#contact` anchor) — no third, competing CTA (no per-service "en savoir plus" links; recommended services render as plain-text/non-interactive cards, resolving RESEARCH.md's Open Question 3 in favor of the stricter SIMU-07 reading) |
| Empty state | Not applicable — the wizard always renders exactly one of: a question, the contact-capture form, or the result screen; there is no data-fetch or user-generated list that can render empty in this phase (parallels Phase 6's static-content reasoning) |
| Error state — submission failure (network error, or the API's `invalid_payload` / `insert_failed` / `notification_failed`) | Heading: **"Une erreur est survenue"** — Body: **"Votre diagnostic n'a pas pu être envoyé. Réessayez, ou contactez-nous directement : [téléphone] / [email]."** Rendered inline within the contact-capture card (never a silent redirect, never a raw error code/technical string shown to the visitor — the API's distinct error strings are for developer/log use only) |
| Destructive confirmation | Not applicable — no delete/reset/irreversible action exists in this phase's UI (see Color section's Destructive row for the full reasoning) |
| RGPD consent checkbox label (SIMU-05, unticked by default) | **"J'accepte que Sèvalys utilise mes réponses pour me recontacter dans le cadre de ce diagnostic."** — immediately followed by an always-visible (not collapsed-by-default) Art. 13 mentions block: responsable du traitement (Sèvalys — Anatholy Bricon, Tours (37), France — contact@sevalys.com), finalité (qualification de la demande et prise de contact), base légale (consentement — la case ci-dessus), durée de conservation (**12 mois** si non converti en client, puis suppression automatique — this is the prospects-table figure from `05-CONTEXT.md` D-04, explicitly **not** the site's separate 3-year contact-form retention figure), droits (accès, rectification, effacement, limitation, opposition, portabilité — exerçables auprès de contact@sevalys.com, réclamation possible auprès de la CNIL) |
| Honeypot field (`website`) | No visible copy — `aria-hidden`, empty, off-screen input per the server-verified contract in `07-RESEARCH.md`. Listed here only to confirm the contract requires zero copy on this field, not to specify any |

## Component & Layout Patterns

*(Extends the template with the phase-specific structural contract the planner/executor need — this phase introduces new component types, not just tokens.)*

**Visual hierarchy:** On every question screen, the question prompt (Heading role) + the selected/hovered answer option is the focal point; the progress bar is a secondary, always-visible confirmation of flow position. On the result screen, the radial gauge is the first-paint focal point (largest accent-colored element), followed by the 2-4 recommended-service cards, followed by the single dual-channel CTA block as the terminal action.

### Wizard shell (SIMU-01, SIMU-04, D-13, D-14, D-15)
- **One question per screen** (D-13) — never all questions on one scrolling page.
- **Progress bar** (D-14): thin rail (4px height, `--line` track, `--acid` fill), fills proportionally as questions are answered — this is the *primary* progress indicator, not a plain step-counter. A `sr-only` text equivalent ("Question 2 sur 5") must still exist for screen readers/accessibility, but is not visually rendered as the primary indicator.
- **Question screen layout:** Heading-role question prompt, then answer options stacked full-width below it. Single-select options render as radio-style buttons; multi-select options render as checkbox-style buttons (D-04) — both use ≥44px-tall button/label elements, `--bg-2` background + `--line` border when idle, `--acid-soft` background + `--acid` border when selected.
- **Nav row** at the bottom of each question screen: "← Précédent" (ghost/secondary style, hidden on question 1) + "Suivant →" (primary, disabled until a value is selected).
- **Contact-capture screen** (step N, gated strictly between the last question and the result per SIMU-04/D-04): nom / email / téléphone native inputs (Body-role labels + inputs, reusing the sitewide hand-rolled form-field convention, not a new component), the RGPD consent checkbox + Art. 13 block (Copywriting Contract), the hidden honeypot `website` field, and the "Obtenir mon diagnostic →" submit button. `formRenderedAt` is captured once at wizard mount (not on this screen) per RESEARCH.md Pitfall 3.
- **Result screen** (step N+1): centered radial gauge, then 2-4 recommended-service cards (plain-text, `--bg-2` surface, service name at Heading role + optional one-line blurb at Body role — **no link, no button** on these cards, per SIMU-07's single-action reading), then the single dual-channel CTA block.

### Gauge visual (SIMU-03, D-09–D-12)
- **Single overall gauge only** — never per-service match bars (D-09).
- Hand-rolled inline SVG, radial/circular (speedometer-style, D-10): 200px diameter, 14px stroke width, rounded linecap, track circle in `--line`, fill arc in `--acid`.
- Score number centered inside the gauge: Display-adjacent size (~36–40px), `--ink` color, weight 500.
- **A framing caption is a required part of this contract, not optional polish** — a bare number with no framing risks reading as a vanity/maturity score, contradicting D-11's urgency framing ("lower score = more opportunity"). Render a Label-role caption near the gauge (e.g. "Score d'opportunité") plus a short dynamic sentence that reframes the number as urgency/opportunity rather than a compliment (exact copy thresholds are Claude's-discretion content per `07-CONTEXT.md`, but the caption's *existence* is locked here).
- Animates via `gsap.to(obj, { v: target, onUpdate })` count-up on result-step mount (not on scroll — Assumption A3 in `07-RESEARCH.md`), mirroring `MethodologySection.tsx`'s existing scrub-to-state pattern. Must respect `prefers-reduced-motion` via the same branch shape as `useReveals()` (skip the tween, jump straight to the final value) — this is a hard `PROJECT.md` constraint, not a nice-to-have.

### Pillar framing (SIMU-08, D-16)
- **Above the wizard:** explainer intro block — Display-role H1, 2-3 short Body-role paragraphs (what the tool does / how it works / why answer honestly) — uses the existing `data-reveal`/`useReveals()` scroll-reveal convention, matching the citable/GEO pillar tone Phase 6 established for `/services/[slug]` pages.
- **Below the wizard (or FAQ block, still on `/simulateur`):** native `<details>`/`<summary>` FAQ items, reusing SVC-05's pattern verbatim — question = `<summary>` at Heading role, answer = always-in-DOM `<p>` at Body role (never conditionally rendered on open state, for crawlability). `FAQPage` JSON-LD is emitted server-side in `layout.tsx` via `buildFaqJsonLd`/`buildJsonLdScript` (reused verbatim from `src/lib/serviceJsonLd.ts`), hardcoded French, matching the same intentional Server-Component-can't-access-`LanguageContext` gap already documented on `/services/[slug]/layout.tsx` (RESEARCH.md Pitfall 6).
